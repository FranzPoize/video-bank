## Problem Statement

The Video Bank app currently has all UI text hardcoded in English. Users need the ability to switch languages via a dropdown in the nav bar.

## Constraints

- Keep code simple and testable
- Avoid inversion of control as much as possible
- Zero new Python dependencies is preferred (stdlib only)
- Must work with existing HTMX patterns
- Must follow existing CSS convention (styles in base.html `<style>` blocks)
- All existing tests must remain passing

## Approach

**Minimal JSON-based i18n system (zero new dependencies).**

Three alternatives considered:

1. **Babel/gettext** (rejected): Adds a new dependency, more complex workflow with `.po`/`.mo` files and extraction tools. Overkill for this small app.

2. **URL-based language paths** (`/fr/videos`) (rejected): Would require restructuring all routes. Cookies are simpler and less invasive.

3. **JSON translations + cookie-based language detection** (chosen):
   - `json` is stdlib — no new dependencies
   - Flat key-value format is simple and human-editable
   - Cookie-based language detection is stateless and works with existing routes
   - Aligns with project's minimal dependency philosophy

## Architecture

```
┌─────────────────────────────────────────────────────────────┐
│  Request Flow                                                 │
├─────────────────────────────────────────────────────────────┤
│                                                               │
│  1. Browser request arrives                                   │

│                                                               │
```

### 2. Shared Templates Module (`app/templates.py` — NEW)

Consolidates the 3 duplicate `Jinja2Templates` instances into one shared module.

**Responsibilities:**
- Creates a single `Jinja2Templates` instance
- Adds `_()` function as a Jinja2 global for translations
- Exposes `current_lang` to templates
- Provides `get_translations(lang)` function that loads JSON files

**Fallback strategy:**
1. Try `translations/{lang}.json`
2. If not found or key missing, fall back to `translations/en.json`
3. If even English key missing, return the key itself (debug-friendly)

### 3. Language Detection Middleware

**Priority order:**
1. **`lang` cookie** (highest priority) — set by the language switcher
2. **`Accept-Language` header** (fallback) — browser's preferred language
3. **Default: `"en"`**

**Implementation:**
- FastAPI middleware (`@app.middleware("http")`) or Starlette `BaseHTTPMiddleware`
- Detects language, loads translations, stores in `request.state`
- The shared `templates` module reads from `request.state` when rendering

**Cookie details:**
- Name: `lang`
- Value: two-letter code (`en`, `fr`, etc.)
- Max-Age: 2592000 (30 days)
- Path: `/`
- SameSite: `Lax`

### 4. Language Dropdown (base.html)

**Position:** Right side of nav bar, after the space indicator.

**HTML structure:**
```html
<nav>
  <a href="/">{{ _("nav.video_bank") }}</a>
  <a href="/upload">{{ _("nav.upload") }}</a>
  <span id="space-indicator" hx-get="/api/space" hx-trigger="load"></span>
  
  <!-- NEW: Language dropdown -->
  <div class="lang-dropdown">
    <button class="lang-btn" id="lang-btn">
      <span class="lang-flag">{{ current_flag }}</span>
      <span class="lang-code">{{ current_lang.upper() }}</span>
      <span class="lang-arrow">▼</span>
    </button>
    <div class="lang-menu" id="lang-menu">
      <a href="#" hx-post="/api/lang" hx-vals='{"lang": "en"}' hx-target="body">
        <span class="lang-flag">🇬🇧</span> English
      </a>
      <a href="#" hx-post="/api/lang" hx-vals='{"lang": "fr"}' hx-target="body">
        <span class="lang-flag">🇫🇷</span> Français
      </a>
    </div>
  </div>
</nav>
```

**CSS (in base.html `<style>`):**
- `.lang-dropdown` — position relative, inline with nav
- `.lang-btn` — matches nav link styling, no underline
- `.lang-menu` — hidden by default, absolute position below button
- `.lang-menu a` — block display, padding, hover background
- Show menu on hover or click (simple JS for click behavior)

**Flag emoji mapping:**
```python
LANG_FLAGS = {
    "en": "🇬🇧",
    "fr": "🇫🇷",
}
# Unknown lang = 🌐
```

### 5. New Endpoint: `POST /api/lang`

**Purpose:** Set the language cookie and redirect/refetch.

**Request:**
- `Content-Type: application/json` or `application/x-www-form-urlencoded`
- Body: `{"lang": "fr"}`

**Response:**
- Sets cookie: `lang=fr; Max-Age=2592000; Path=/; SameSite=Lax`
- Returns `HX-Redirect: request.headers.get("Referer", "/")` header
- HTMX sees `HX-Redirect` and reloads the page

**Fallback for non-HTMX:** Returns `RedirectResponse` to referer or `/`.

### 6. JavaScript i18n

JS files (`upload.js`, `clipper.js`) have hardcoded English strings. These need translation too.

**Approach:** Export translations via inline `<script>` in `base.html`:

```html
<script>
window.TRANSLATIONS = {
    "upload.untitled": "{{ _('upload.untitled') }}",
    "upload.completed": "{{ _('upload.completed') }}",
    // ... all JS-accessible strings
};
</script>
```

**JS usage:**
```javascript
// Before:
statusEl.textContent = "Completed";

// After:
statusEl.textContent = window.TRANSLATIONS["upload.completed"] || "Completed";
```

**Alternative helper:**
```javascript
function _(key) {
    return window.TRANSLATIONS[key] || key;
}
// Usage: _("upload.completed")
```

## Data Flow

### Page Render Flow

```
1. User navigates to /
   └── Request: Cookie: lang=fr

2. Middleware runs
   ├── Detects lang=fr from cookie
   ├── Loads translations/fr.json
   ├── Stores in request.state.translations
   └── request.state.current_lang = "fr"

3. Route handler runs (GET /)
   └── returns templates.TemplateResponse(request, "index.html", {...})

4. Jinja2 renders
   ├── templates module reads request.state
   ├── Makes _() function available
   ├── {{ _("nav.video_bank") }} → "Banque de vidéos"
   └── current_lang variable available for dropdown

5. Response sent
   └── HTML with translated text
```

### Language Switch Flow

```
1. User clicks "🇫🇷 Français" in dropdown
   └── hx-post="/api/lang" hx-vals='{"lang": "fr"}'

2. POST /api/lang handler runs
   ├── Validates lang code (must be in supported list)
   ├── Sets cookie: lang=fr, Max-Age=30 days
   └── Returns HX-Redirect header to referer page

3. HTMX sees HX-Redirect
   └── Triggers full page reload with new cookie

4. Page reloads with French text
   └── Cookie is now lang=fr, middleware detects it
```

## Error Handling

| Scenario | Behavior |
|----------|----------|
| `lang` cookie has invalid code | Falls back to Accept-Language, then "en" |
| Translation file missing for lang | Falls back to en.json |
| Specific key missing in translation | Falls back to en.json value |
| Key missing even in en.json | Returns the key itself (e.g., `"nav.unknown"`) |
| `POST /api/lang` with invalid lang | Ignores, keeps current language, redirects anyway |
| Referer header missing on lang switch | Redirects to `/` (homepage) |

**Fails-open design:** The app never crashes due to translation issues. Missing keys are visible in the UI (key names), making debugging easy.

## Testing Strategy

### New tests in `tests/test_i18n.py`:

1. **`test_default_language_english`** — Request without cookie, verify English text in response.

2. **`test_language_cookie`** — Request with `Cookie: lang=fr`, verify French text in response.

3. **`test_language_switch_endpoint`** — `POST /api/lang` with `{"lang": "fr"}`, verify `set-cookie` header in response.

4. **`test_invalid_language_fallback`** — Request with `Cookie: lang=invalid`, verify falls back to English.

5. **`test_translation_key_fallback`** — Unit test for `get_translations()`: verify missing key returns English value.

### Mocking strategy:

```python

    "/api/lang",

```

## Open Questions

1. **Supported languages:** Design assumes English (`en`) + French (`fr`). Add more by:
   - Creating `translations/{lang}.json`
   - Adding entry to `LANG_FLAGS` mapping
   - Adding link to dropdown in `base.html`

2. **Right-to-left (RTL) languages:** Not needed for v1 (EN/FR are LTR). Future support would require:
   - `dir="rtl"` attribute on `<html>` when appropriate
   - CSS adjustments for text alignment, dropdown position

3. **URL-based language paths:** Not implemented in v1. Would require:
   - Route prefixes (`/en/`, `/fr/`)
   - Middleware to strip prefix and set language
   - All internal links need language prefix

4. **Python route error messages:** These are API responses (e.g., "Video not found"). Low priority for v1 since they're not primary UI text. Can be added later if needed.

5. **Number/date formatting:** Not in scope for v1. The app currently shows:
   - File sizes: "MB" (unit, not formatted number)
   - Dates: SQLite datetime, rendered as-is
   Future i18n could add locale-aware formatting.
